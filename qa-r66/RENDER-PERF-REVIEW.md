# StoryWorld 이동 렉: 성능 검토와 후보 수정

**후보 소스 SHA:** `b48b49666c8556f790c04735a8680646a41782a9`  
**기준 `origin/main`:** `51490741b5786f59fb3fce2cf36f03343cd3e65c`  
**상태:** 별도 로컬 브랜치, 공개하지 않음.

## 사용자 PC 보고서 반영

사용자가 보낸 Edge `about:gpu` 보고서를 확인했다. Edge 154.0.4258.37 / Windows 10.0.26200.9550에서 **NVIDIA GeForce RTX 4060 Ti가 활성 GPU**이며 GL 렌더러는 `ANGLE (NVIDIA ... Direct3D11)`이다. WebGL, Canvas, Compositing, Rasterization이 모두 `Hardware accelerated`이고 GPU 프로세스 충돌 수는 0이다.

따라서 사용자의 실제 PC 렉을 SwiftShader/소프트웨어 렌더링 탓으로 돌릴 근거는 없다. 이 환경의 헤드리스 브라우저는 SwiftShader를 써서 실제 PC 상태를 재현하지 못했다. 강한 그래픽카드가 있어도 자바스크립트의 메인 스레드 작업은 GPU가 대신하지 않는다. 현재 코드에서 가장 의심되는 구간은 이동 때마다 실행되는 화면 명령 수집, 맵 가시성·바닥 타일 투영, Three 장면의 기하 비교·갱신이다. 다만 사용자 PC의 Performance trace는 아직 받지 않아 이 원인을 실제 기기에서 확정하지 않았다.

## 병목 조사

기준 코드의 메인 스레드 계측에서 `draw()` 중앙 처리 시간은 실행별 p50 약 65.7–74.5ms, p95 약 95.4–123.3ms였다. 같은 표본에서 `tick()` p50은 약 1.0–1.2ms, HUD 갱신은 약 0.8–0.9ms였다. 이 실행에서 긴 작업은 게임 시뮬레이션 틱이나 HUD보다 그리기 경로에 집중됐다. 표본 프로파일의 앱 함수에는 `explorationBlocked` 약 85–113ms, `texturedFloor` 약 84–106ms, `geometry` 약 60–89ms가 6초 구간에서 관찰됐다. 이는 같은 테스트 환경의 프로파일 합계 표본이며 프레임 지연 시간과 더해서 해석하지 않는다.

3초 이동 캡처 후 명령 장면 진단에는 161개 명령 메시, 텍스처 7개, 기하 업데이트 2,101회, 전체 기하 비교 5,514회, 카메라 평행 이동 비교 3,275회가 기록됐다. 카운터는 페이지 준비와 워밍업을 포함한 누계이므로 초당 호출 수는 아니다. GPU draw-call 수를 직접 잰 값도 아니다.

## 바꾼 점과 측정 결과

- 모든 화면 명령에 붙던 미사용 `screenPosition` 정점 배열을 그라디언트 명령에만 붙인다. 같은 장면에서 이전 배열 40,392바이트 대비 후보 1,200바이트(약 97% 감소 추정)다. 총 JavaScript 힙이나 GPU 메모리 감소량을 뜻하지 않는다.
- 반복 카메라 이동은 작은 Float32 좌표 변화량을 계속 더하지 않고 기준 좌표와 절대 이동량으로 계산한다. 20만 회 이동 및 중간 재중심화 검사에서 최대 좌표 오차는 `0.00000733px`였다.
- 매 프레임 명령 캡처의 `filter().map()` 임시 배열과 명령/소유자 객체 복사를 없애고 현재 프레임 명령을 제자리에서 정리한다. 색상·이미지·그라디언트 명령 수 207개는 변경 전후 동일했다.
- 카메라 평행 이동 비교를 전체 기하 비교와 별도로 센다. 광선 장애물 수 0은 0으로 유지되게 진단값을 수정한다.

| 같은 헤드리스 SwiftShader 이동 장면 | 기준 3회 중앙값 | 최종 후보 3회 중앙값 |
|---|---:|---:|
| 프레임률 | 4.308 FPS | 4.492 FPS |
| 프레임 간격 p50 | 200ms | 200ms |
| 프레임 간격 p95 | 266.7ms | 266.7ms |

프레임률 중앙값은 약 4.3% 높지만 각 실행 분포가 크게 겹친다. 이 실행 결과로 사용자 PC의 체감 개선을 주장할 수 없다. 별도 계측에서 기준/후보 `draw()` 평균은 62.79/62.74ms, p50은 69.3/71.4ms, p95는 109.7/103.2ms였다. 캡처 함수만 분리한 새 컨텍스트 3개씩의 평균 중앙값도 기준 2.528ms, 후보 2.675ms였고 p50 2.3/2.4ms로 후보가 빨라졌다고 확인되지 않았다. 따라서 임시 할당을 줄인 코드는 유지했지만 유의미한 메인 스레드 속도 향상으로 보고하지 않는다. 힙 증감은 GC 시점 변동이 커서 비교 결론을 내리지 않았다.

## 검증과 한계

- CPU 검사 통과: 카메라 이동 200,000회, 재중심화, 0 광선 장애물 수, 카메라 비교/기하 비교 카운터 분리.
- 브라우저 캡처와 손전등 회귀 통과: 후보에서 손전등 마스크 켬/끔, 터치, 저장/불러오기, 세로/가로 전환. iPhone 에뮬레이션이며 실제 휴대전화 검증은 아니다. 페이지 오류 없음.
- 협동 회귀 통과: 로컬 두 페이지 클라이언트 시뮬레이션만 실행했다. 공개 중계 서버나 네트워크 회귀가 아니다.
- 정적 Pages 재구성 통과: 런타임 1,906개 파일, 출력 1,908개, 아카이브 87개. HEAD 1,906개와 오디오 범위 276개 검증도 통과했다. 원본 ZIP 아카이브 내용은 변경하지 않았다.
- 실제 사용자 PC에서 게임 프레임 계측, 실제 GPU draw-call/메모리 계측, 실기기 검증은 하지 않았다. 사용자가 `Trace-20261017T184402.json.gz` trace 파일을 첨부했다. 파일명과 35.4MB 크기까지 전달됐지만 본문 다운로드가 실행 환경 네트워크 프록시에서 HTTP 403으로 거절됐다. 따라서 이 trace는 파싱하지 못했고, 사용자 PC의 실제 작업표본이라고 보고서에서 해석하지 않는다.
- 임시 자동 레거시 렌더러 전환은 제외했다. 같은 시드·장면 화면에서 레거시에는 퀘스트와 미니맵 UI가 보였지만 Three 화면에는 없었다. 서로 다른 렌더 품질 간 FPS를 같은 개선으로 비교하지 않는다.

## 배포와 다음 진단

후보는 로컬 커밋에만 있다. main 병합, push, Pages 공개 재배포, Render/중계 서버 변경은 하지 않았다. 이 환경에서 공개 Pages 응답을 직접 확인할 수 없어 현재 서비스된 파일이 어느 커밋인지 독립 검증하지 못했다.

실제 PC 원인을 확정하려면 trace 본문을 이 환경에서 읽을 수 있어야 한다. 현재 첨부는 다운로드 경로가 프록시에서 차단돼 분석하지 못했다. 파일을 다시 내보내거나 압축을 풀어 올리면 긴 메인 스레드 작업, WebGL 호출 제출, GPU 대기를 분리해 다음 변경을 결정할 수 있다.
