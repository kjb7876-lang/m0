# StoryWorld 이동 렉: 성능 검토와 후보 수정

**후보 소스 SHA:** 최종 검증 후 기록
**기준 `origin/main`:** `51490741b5786f59fb3fce2cf36f03343cd3e65c`  
**상태:** 배포 준비 중인 별도 브랜치 후보.

## 사용자 PC 보고서 반영

사용자가 보낸 Edge `about:gpu` 보고서를 확인했다. Edge 154.0.4258.37 / Windows 10.0.26200.9550에서 **NVIDIA GeForce RTX 4060 Ti가 활성 GPU**이며 GL 렌더러는 `ANGLE (NVIDIA ... Direct3D11)`이다. WebGL, Canvas, Compositing, Rasterization이 모두 `Hardware accelerated`이고 GPU 프로세스 충돌 수는 0이다.

따라서 사용자의 실제 PC 렉을 SwiftShader/소프트웨어 렌더링 탓으로 돌릴 근거는 없다. 이 환경의 헤드리스 브라우저는 SwiftShader를 써서 실제 PC 상태를 재현하지 못했다. 강한 그래픽카드가 있어도 자바스크립트의 메인 스레드 작업은 GPU가 대신하지 않는다. 현재 코드에서 가장 의심되는 구간은 이동 때마다 실행되는 화면 명령 수집, 맵 가시성·바닥 타일 투영, Three 장면의 기하 비교·갱신이다. 다만 사용자 PC의 Performance trace는 아직 받지 않아 이 원인을 실제 기기에서 확정하지 않았다.

## 병목 조사

사용자가 Library 이미지에서 직접 확인해 준 Edge Performance profile 표본은 아래와 같다. trace 파일 자체는 이 실행 환경에서 아직 직접 압축 해제/파싱하지 못했고, 선택된 시간 구간과 profile 화면의 빌드 SHA도 확인되지 않았다. 따라서 이 값을 특정 배포 버전이나 프레임별 시간으로 단정하지 않는다.

| 사용자 Edge 프로파일 항목 | Self time | Total time |
|---|---:|---:|
| `drawImage` | 8,305.9ms (35.0%) | 8,313.6ms (35.0%) |
| `cropped` | 3,235.7ms (13.6%) | 9,589.7ms (40.4%) |
| `getContext` | 2,312.6ms (9.7%) | 2,313.8ms (9.7%) |
| `Commit` | 1,209.0ms (5.1%) | — |
| C++ GC | 1,074.0ms (4.5%) | — |
| MajorGC | 709.2ms (3.0%) | — |

Call tree의 inclusive/total 시간은 호출 계층에서 겹칠 수 있어 합산하지 않는다. `getContext` 표본만으로 매 호출마다 새 context를 만들었다고 볼 수는 없다. 다만 저장소의 R55 `cropped(rect,mip)` 구현에서 캐시 hit마다 LRU Map을 삭제·재삽입하고, 96개 제한에 도달하면 crop canvas를 반복 퇴출했다. 동일한 이동 장면의 로컬 계측에서는 이 동작으로 `cropped` miss가 새 canvas/context 및 원본 `drawImage`와 함께 반복됐다. 이는 사용자가 전달한 호출 이름들과도 맞는 저장소 수준의 재현 가능한 원인이다.

기준 코드의 메인 스레드 계측에서 `draw()` 중앙 처리 시간은 실행별 p50 약 65.7–74.5ms, p95 약 95.4–123.3ms였다. 같은 표본에서 `tick()` p50은 약 1.0–1.2ms, HUD 갱신은 약 0.8–0.9ms였다. 이 실행에서 긴 작업은 게임 시뮬레이션 틱이나 HUD보다 그리기 경로에 집중됐다. 표본 프로파일의 앱 함수에는 `explorationBlocked` 약 85–113ms, `texturedFloor` 약 84–106ms, `geometry` 약 60–89ms가 6초 구간에서 관찰됐다. 이는 같은 테스트 환경의 프로파일 합계 표본이며 프레임 지연 시간과 더해서 해석하지 않는다.

3초 이동 캡처 후 명령 장면 진단에는 161개 명령 메시, 텍스처 7개, 기하 업데이트 2,101회, 전체 기하 비교 5,514회, 카메라 평행 이동 비교 3,275회가 기록됐다. 카운터는 페이지 준비와 워밍업을 포함한 누계이므로 초당 호출 수는 아니다. GPU draw-call 수를 직접 잰 값도 아니다.

## 바꾼 점과 측정 결과

- 모든 화면 명령에 붙던 미사용 `screenPosition` 정점 배열을 그라디언트 명령에만 붙인다. 같은 장면에서 이전 배열 40,392바이트 대비 후보 1,200바이트(약 97% 감소 추정)다. 총 JavaScript 힙이나 GPU 메모리 감소량을 뜻하지 않는다.
- 반복 카메라 이동은 작은 Float32 좌표 변화량을 계속 더하지 않고 기준 좌표와 절대 이동량으로 계산한다. 20만 회 이동 및 중간 재중심화 검사에서 최대 좌표 오차는 `0.00000733px`였다.
- 매 프레임 명령 캡처의 `filter().map()` 임시 배열과 명령/소유자 객체 복사를 없애고 현재 프레임 명령을 제자리에서 정리한다. 색상·이미지·그라디언트 명령 수 207개는 변경 전후 동일했다.
- 카메라 평행 이동 비교를 전체 기하 비교와 별도로 센다. 광선 장애물 수 0은 0으로 유지되게 진단값을 수정한다.
- R55 crop cache의 key 생성에서 매번 만드는 `rect.map()` 임시 배열을 없애고, cache hit마다 Map 항목을 삭제·재삽입하지 않도록 했다. 최대 엔트리를 96에서 1,024로 올렸지만 기존 6MiB 픽셀 메모리 상한은 그대로 둔다. 같은 이동 실험에서 201개의 crop이 1.84MiB를 차지해 상한 아래에 있었다.
- 사용자 요청에 따른 손전등 오류도 함께 고쳤다. 꺼진 상태일 때 남던 18% 텍스처를 제거하고 마스크 밖을 검정으로 렌더링하며, 벽 재질에도 같은 마스크를 적용한다. 2D draw-command의 fragment 좌표를 Three의 카메라 월드 좌표처럼 잘못 해석하던 매핑도 화면 좌표에서 `Projection.screenToWorld` 역변환을 사용하도록 수정했다.

### 이전 Three 렌더러 구조 변경 측정

아래 표는 별도 Three 렌더러 단계의 과거 비교이며, 아래 crop-cache 표와는 렌더 경로가 다르다.

| 같은 헤드리스 SwiftShader 이동 장면 | 기준 3회 중앙값 | 해당 후보 3회 중앙값 |
|---|---:|---:|
| 프레임률 | 4.308 FPS | 4.492 FPS |
| 프레임 간격 p50 | 200ms | 200ms |
| 프레임 간격 p95 | 266.7ms | 266.7ms |

프레임률 중앙값은 약 4.3% 높지만 각 실행 분포가 크게 겹친다. 이 실행 결과로 사용자 PC의 체감 개선을 주장할 수 없다. 별도 계측에서 기준/후보 `draw()` 평균은 62.79/62.74ms, p50은 69.3/71.4ms, p95는 109.7/103.2ms였다. 캡처 함수만 분리한 새 컨텍스트 3개씩의 평균 중앙값도 기준 2.528ms, 후보 2.675ms였고 p50 2.3/2.4ms로 후보가 빨라졌다고 확인되지 않았다. 따라서 임시 할당을 줄인 코드는 유지했지만 유의미한 메인 스레드 속도 향상으로 보고하지 않는다. 힙 증감은 GC 시점 변동이 커서 비교 결론을 내리지 않았다.

추가로 병목 수정 전후 각각 2회, 같은 소프트웨어 에뮬레이션 조건에서 측정했다.

| 같은 6초 이동 장면 · 중앙값 | 기준 | 후보 |
|---|---:|---:|
| `draw()` 평균 / p95 | 39.76 / 53.75ms | 20.53 / 26.95ms |
| 프레임 간격 평균 / p95 | 139.39 / 158.30ms | 111.10 / 125.05ms |
| 프레임률(평균 간격 기반) | 7.17 FPS | 9.01 FPS |
| Crop cache entries / pixel bytes | 96 / 982,784B (0.94MiB) | 201 / 1,835,008B (1.75MiB) |
| Cache miss / context / source `drawImage` | 5,344회 / 각 5,344회 | 각 68회 |
| Cache eviction | 5,344회 | 0회 |

후보에서 `draw()` 평균은 약 48%, p95는 약 50%, 프레임 간격 평균은 약 20% 낮았다. cache miss/context/source `drawImage` 반복도 줄었다. 이는 같은 컨테이너/브라우저의 2회 비교이며 측정 변동과 headless CPU 환경의 한계가 있다. 후보의 캐시 pixel bytes는 증가했지만 기존 6MiB 상한 안에 있었다. 사용자 RTX 4060 Ti 또는 실제 Edge 프레임률의 개선 수치로 환산하지 않는다. GC 민감한 JS heap은 결론에 쓰지 않는다.

## 검증과 한계

- CPU 검사 통과: 카메라 이동 200,000회, 재중심화, 0 광선 장애물 수, 카메라 비교/기하 비교 카운터 분리.
- 브라우저 캡처와 손전등 회귀 통과: 후보에서 손전등 마스크 켬/끔, 터치, 저장/불러오기, 세로/가로 전환 및 데스크톱 기본 OFF 상태에서 ON 전환. 마스크 바깥의 샘플은 RGB 각 채널 4–11이며 검정에 가까운 결과였다. iPhone 에뮬레이션이며 실제 휴대전화 검증은 아니다. 페이지 오류 없음.
- 협동 회귀 통과: 로컬 두 페이지 클라이언트 시뮬레이션만 실행했다. 공개 중계 서버나 네트워크 회귀가 아니다.
- 정적 Pages 재구성 통과: 런타임 1,906개 파일, 출력 1,908개, 아카이브 87개. HEAD 1,906개와 오디오 범위 276개 검증도 통과했다. 원본 ZIP 아카이브 내용은 변경하지 않았다.
- 실제 사용자 PC에서 후보를 실행해 프레임 시간·GPU draw-call·메모리를 다시 계측하지 않았고, 실기기 검증도 하지 않았다. `Trace-20261017T184402.json.gz`는 실행 환경에서 직접 파싱하지 못했지만, 사용자가 Library 프로파일 화면의 위 수치를 확인해 제공했다. 화면 구간 및 빌드 SHA가 미상이라 그 값은 사용자 PC profile 표본으로만 기재했다.
- 임시 자동 레거시 렌더러 전환은 제외했다. 같은 시드·장면 화면에서 레거시에는 퀘스트와 미니맵 UI가 보였지만 Three 화면에는 없었다. 서로 다른 렌더 품질 간 FPS를 같은 개선으로 비교하지 않는다.

## 배포와 다음 진단

이 보고서 작성 시점에는 후보가 로컬 브랜치에 있다. 사용자 요청에 따라 검증·커밋 후 GitHub Pages로 배포한다. Render/중계 서버 설정은 작업 범위에서 제외한다. 공개 Pages 반영 여부와 응답 파일은 push 후 별도로 확인해 기록한다.

실제 PC 원인을 확정하려면 trace 본문을 이 환경에서 읽을 수 있어야 한다. 현재 첨부는 다운로드 경로가 프록시에서 차단돼 분석하지 못했다. 파일을 다시 내보내거나 압축을 풀어 올리면 긴 메인 스레드 작업, WebGL 호출 제출, GPU 대기를 분리해 다음 변경을 결정할 수 있다.
